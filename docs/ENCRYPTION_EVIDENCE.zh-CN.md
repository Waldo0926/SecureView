# 如何证明文件真的被加密了

[English](ENCRYPTION_EVIDENCE.md) | [简体中文](ENCRYPTION_EVIDENCE.zh-CN.md)

文件列表会同时显示每个文件的原始大小和加密后大小，而且两者相同。第一次看到的人很自然会问：到底有没有加密，
还是只改了文件名？本页回答这个问题，说明如何现场演示，并写清楚这些证据能证明什么、不能证明什么。

## 为什么两个大小一样

SecureView 使用 AES-128/192/256-GCM、AES-256-GCM-SIV、ChaCha20-Poly1305 或 XChaCha20-Poly1305。它们都是**流式**认证加密：逐字节加密，**没有填充**，
所以密文长度与原文件完全相同。另外有两样小东西，但都不是追加在文件后面的：

| 项目 | 大小 | 存放位置 |
| --- | --- | --- |
| Nonce（即 “IV”） | 12 字节（XChaCha20-Poly1305 为 24 字节） | 数据库中该文件的元数据行 |
| 认证标签 | 16 字节 | 同一元数据行，与密文**分开存放** |

后端强制执行这一点：如果上传的密文长度与声明的原始大小不一致，会被拒绝
（[`docs/crypto/FILE_ENVELOPE.md`](crypto/FILE_ENVELOPE.md) 第 4 节）。

如果你预期文件会变大，想到的是 AES-CBC 这类分组模式：它按 16 字节分组填充，并在前面加 IV。本项目有意只提供带认证的模式，
因为 AES-CBC 和 AES-CTR 会丢掉完整性保证。

所以**大小相同是预期结果，大小不同才是 bug。**文件列表会四舍五入（两个都是“7.54 MB”），把鼠标悬停在大小单元格上可以看到精确的字节数。

## 现场演示

1. **My Files → Encrypted preview**（每个文件下方，自己的和别人分享给你的都有）。它显示算法、以字节为单位的精确大小、
   上传时记录的 SHA-256，以及服务器存储的前 128 字节的十六进制转储。对 `.pdf`、`.docx`、`.zip`、`.png` 等类型，
   它还会把开头几个字节与**未加密**文件的典型开头对比（PDF 是 `25 50 44 46`，Word 文档是 `50 4b 03 04`），并说明
   那个文件头是否可见。万一可见，面板会变红。
2. **Download encrypted file** 会把完整的存储对象保存为 `<文件名>.ciphertext`。任何应用都打不开它，这正是重点。然后在终端里：

   ```bash
   xxd notes.txt.ciphertext | head        # 看起来随机的字节，没有可读文字
   shasum -a 256 notes.txt notes.txt.ciphertext   # 两个不同的摘要
   ls -l notes.txt notes.txt.ciphertext   # 大小相同，原因如上
   ```

3. **改动 `.ciphertext` 文件中的一个字节**再尝试解密：认证会失败，而不是解出一堆乱码。篡改状态测试和隔离的篡改演练就是端到端地展示这一点。

## 测试套件里的证据

`frontend/src/crypto/encryption-evidence.test.ts` 把一个 **20 MiB** 的文件（由重复的英文句子构成，是最容易辨认的明文）
用六种算法分别经由真实的 `prepareUpload` 流程处理，并检查结果。在 Apple M4、Node 22 上的一次运行（2026-10-02）：

| 算法 | 字节数 输入 → 输出 | 熵（比特/字节） | 与原文件相同的字节占比 | 加密 + 自检用时 |
| --- | --- | --- | --- | --- |
| AES-256-GCM | 20,971,520 → 20,971,520 | 4.441 → 7.99999 | 0.392 % | 0.07 秒 |
| AES-256-GCM-SIV | 20,971,520 → 20,971,520 | 4.441 → 7.99999 | 0.389 % | 0.51 秒 |
| ChaCha20-Poly1305 | 20,971,520 → 20,971,520 | 4.441 → 7.99999 | 0.390 % | 0.18 秒 |
| XChaCha20-Poly1305 | 20,971,520 → 20,971,520 | 4.441 → 7.99999 | 0.390 % | 0.18 秒 |
| AES-192-GCM | 20,971,520 → 20,971,520 | 4.441 → 7.99999 | 0.391 % | 0.05 秒 |
| AES-128-GCM | 20,971,520 → 20,971,520 | 4.441 → 7.99999 | 0.391 % | 0.05 秒 |

用时一列不是基准测试，但能看出真实差别：AES-GCM 几行用的是浏览器内置、带硬件加速的 AES，而 AES-256-GCM-SIV 和两种 ChaCha
用的是 JavaScript 库（`@noble/ciphers`）。ChaCha 在 JavaScript 里依然很快；AES-GCM-SIV 大约比内置 GCM 慢十倍，对 500 MB 的文件
在笔记本上大约多几秒。

各列的含义：熵的最大值是 8，而结构化的明文只有 4.4；“与原文件相同的字节占比”是密文与明文在同一位置恰好是相同字节的比例，
0.391 %（1/256）正是互不相关的数据应有的值。对每种算法，测试还断言：SHA-256 不同、没有相同的 64 字节前缀、解密能得到
完全一致的原文件、并且改动中间任意一个字节会让认证失败。这个测试在每个 PR 的 CI 中运行。本地重跑：

```bash
cd frontend && npx vitest run src/crypto/encryption-evidence.test.ts --reporter=verbose
```

## 这些证据不能证明什么

- **这不是密码分析。**高熵对好的加密是必要条件，而非充分条件：弱密码的输出看起来也是随机的。对算法本身的信心来自：通过 WebCrypto
  和经过审查的库使用标准算法，以及 `docs/crypto/test_vectors.json` 中的已知答案向量，而不是这张表。
- **数字来自 Node。**它运行的是与浏览器相同的 TypeScript，但密码学后端不同。浏览器本身由 Chromium 黄金路径测试
  （`e2e-live` Job）检查：它上传一个文件，并断言存储的字节不是以原文件的开头开始的。
- **大小是 20 MiB，不是 500 MiB。**上传上限是 500 MiB。非常大的文件受限于浏览器内存，而不是密码算法
  （威胁模型 F-19，以及上传页上的提示）。
- **一个只是被信任的服务器也会显示同样的界面。**预览读取的是服务器存放的内容；让它有意义的是服务器从未收到密钥，这是设计的性质
  （`docs/SECURITY_FLOWS.md`），而不是本页的性质。
