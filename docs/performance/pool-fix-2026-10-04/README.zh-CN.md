# 修复 100 用户时数据库连接池耗尽的问题（2026-10-04）

[English](README.md) | [简体中文](README.zh-CN.md)

#140 的 staging 压测（[报告](../REPORT-2026-10-03.md)）找到了第一个瓶颈：100 个并发用户时，65–78% 的上传返回 HTTP 500，
错误是 `QueuePool limit of size 5 overflow 10 reached`，而服务器 CPU 平均只有 3%。本页记录了原因是怎么找到的、一次反而
让情况变糟的修复，以及最终有效的修复。修复前后都用同一个压测工具测量。

## 结果

同一台机器、同一个工具、同一批账号，命令是 `steps --users 20,50,100 --duration 30 --size 1MiB`，测试对象是本地 API 和
MySQL 8.4（一台笔记本，不是 staging 服务器）：

| 并发用户 | 修复前：上传失败 | 修复前：每秒操作 | 修复前：上传 p95 | 修复后：上传失败 | 修复后：每秒操作 | 修复后：上传 p95 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | 0% | 53.6 | 224 ms | 0% | 58.4 | 198 ms |
| 50 | 0% | 54.5 | 470 ms | 0% | 56.1 | 515 ms |
| **100** | **80%**（HTTP 500） | **0.33** | **60.5 秒** | **0%** | **56.1** | **969 ms** |

修复前，100 用户时吞吐量几乎降到零，失败原因和 staging 上看到的连接池超时完全一样，所以本地压测复现了 staging 的问题。
本地网络很快，这也说明问题和网速无关。修复后，每一档的吞吐量都稳定在每秒约 56 次，延迟随排队增加，这是本机自身的上限。
原始汇总和图表见 [`before/`](before/REPORT.md) 和 [`after/`](after/REPORT.md)。

## 原因是怎么找到的

1. **第一个推测是错的，测量推翻了它。** 报告里推测"文件传输期间可能一直占着数据库连接"。我们故意用三个很慢的客户端下载
   一个 30 MB 的文件，同时观察 MySQL：传输期间**没有任何未结束的事务**。下载服务在开始传输前就提交了，连接已经还回连接池。
2. **在本地复现了问题**（见上表的 100 用户），这样就不需要占用 staging 服务器来排查。日志显示，每一次超时都发生在认证这一步。
3. **真正的原因：** 上传接口是 `async` 的。认证之后，连接没有归还；接着上传在事件循环上直接执行数据库调用，并且每写一块
   暂存文件就要等一次线程池，整个过程都占着这个连接。100 个用户时，15 个上传占满了全部 15 个连接、都在等线程，而线程池
   的 40 个线程全被等连接的请求占着。谁都动不了，直到 30 秒后连接池超时。

## 让情况变糟的那次修复

第一次只做了"认证后、暂存前归还连接"，结果连 **50 个用户**也变慢了（下载 p95 达到 30 秒）。原因是上传剩下的数据库调用
仍然在事件循环上执行，于是变成了*在事件循环上等连接*，所有请求都会被冻结最长 30 秒。这一版没有提交上线。

## 最终的修复

- `FileService.upload` 拆成三段：在线程池里做前置检查（查密钥、查限额，然后归还连接）；异步暂存文件（不持有连接）；在线程池
  里写入记录（数据行、审计、发布、提交，回滚和补偿逻辑保持不变）。事件循环上不再有任何数据库调用，等待线程池时也不持有连接。
- 认证依赖（`get_current_actor`）结束它的只读事务，所以任何请求都不会把认证时拿到的连接带进接口。
- 测试：新增单元测试，检查暂存之前已经归还连接；故障注入测试改为在写入文件记录的那次提交时杀掉连接；后端在真实 MySQL 上
  633 个测试全部通过，覆盖率 85.28%。

## staging 重跑（2026-10-04 晚）

工具和参数与 2026-10-03 那次完全相同（`steps --users 5,50,100,5 --duration 60 --size 1MiB`），通过 SSH 隧道压测 staging，
期间暂停了自动部署、CI runner 和备份。原始数据、服务器监控和报告见 [`staging-rerun/`](staging-rerun/REPORT.md)。

| 100 个并发用户 | 修复前（10-03） | 修复后（10-04） |
| --- | ---: | ---: |
| 上传成功 | 23 / 103（**78% 失败，HTTP 500**） | **102 / 102，0 失败** |
| 下载解密并与原文 SHA-256 比对一致 | 23 | 102，完整性失败 0 次 |
| 上传吞吐 | 0.19 次/秒 | 0.86 次/秒 |

修复在真实服务器上同样有效，不只是笔记本上的结果。两点要如实说明：测试机的家用网络仍然决定了所有延迟数字（100 用户一次上传
中位数约 61 秒）；第一档 5 用户出现了 4 次连接中断（`RemoteProtocolError`），上次 50 用户那档也有过，服务器日志里没有对应记录，
很可能是线路或隧道造成的，没有再深入排查。压测期间服务器日志没有任何错误。
