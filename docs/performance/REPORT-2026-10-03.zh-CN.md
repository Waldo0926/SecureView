## 测试条件——引用任何数字前先读

- **压测机：** 家庭网络上的一台笔记本，通过 SSH 隧道访问 `127.0.0.1:8000` 上的 API（不经过 nginx、没有 TLS，所以
  测的不是 nginx 的按 IP 限流）。服务器 sshd 禁止端口转发；为本次测试临时加了一个 `PermitOpen 127.0.0.1:8000`
  例外，测完已删除。
- **限制所有传输数字的是网络，不是服务器。** 测试期间实测：VPS 自己的端口双向约 92–98 Mbit/s（到 Cloudflare），
  但家庭 → VPS 单连接只有约 24 Mbit/s 上行、13 Mbit/s 下行（四连接 41 Mbit/s）。这就是为什么从 5 个用户起总吞吐量
  一直停在每秒 1–3 次操作、而服务器 CPU 只有几个百分点，也是延迟随用户数增长的原因。大文件耗时是这条链路下的
  数字；服务器自身的上限是约 100 Mbit/s 的端口（500 MiB 至少约 45 秒）。
- **`RemoteProtocolError` 是客户端一侧的。** 从 10 个用户起（以及每用户 2 个以上任务时），部分上传以
  `RemoteProtocolError` 失败。同一时段后端日志只有 200/201 响应，observe 任务统计的服务器错误为 0，所以这是单条 SSH
  隧道在负载下断连，而不是应用的问题。510 次失败中有 296 次属于这种。
- **失败构成（510 次）：** 296 次隧道侧 `RemoteProtocolError`；151 次 100 用户时连接池耗尽导致的 HTTP 500；58 次登录
  并发上限导致的 HTTP 429（有意为之）；5 次发生在断网时。
- **60 分钟长稳测试在 58 分钟处截断。** 压测机的家庭网络在 02:31:44 断开；之后每个请求都在到达服务器前以
  `ConnectError` 失败（后端没有记录错误，也没有重启）。摘要保留了断网前开始的 7,159 次操作；未截断的文件是
  `raw/mixed-20261003T173402Z/summary.untruncated.json`。
- **长稳测试中的延迟漂移**（约 10–15 分钟后 p95 上升）在服务器一侧没有对应现象：CPU、RSS、数据库连接和错误数
  都平稳。有两个可能原因，本次未能区分：晚间的家庭网络，以及每个测试账户积累了数千个文件后 `list` 变慢（5 分钟
  测试中 list p95 为 336 ms，58 分钟测试中为 612 ms）。
- **服务器当时没有其他负载：** 备份、异地备份、对账、完整性巡检、安全 Agent 和自动部署的定时器在测试期间暂停；
  清理后手动跑了一次备份和异地备份，然后重新启用所有定时器。100 个测试账户及其文件都通过 API 删除
  （`cleanup`，100 × HTTP 200）；磁盘 172 G → 192 G → 173 G。

## 需处理的发现

1. **数据库连接池是第一个瓶颈。** *2026-10-04 更新：下面的猜测是错的，问题已修复（PR #163）。* 慢速下载在传输
   期间并不占用事务；真正的原因是上传在等待线程池时占着连接，而线程池的线程又都在等连接。本地同样的 100 用户
   阶段从 80% 上传失败、每秒 0.33 次操作，变为零失败、每秒 56 次；见
   [pool-fix-2026-10-04/](pool-fix-2026-10-04/README.zh-CN.md)。2026-10-04 晚又在 staging 上重跑：100 用户时 102/102 次上传、
   102/102 次校验下载全部成功。原来的猜测保留作记录：请求在慢速客户端仍在收发文件体时一直持有数据库连接。
2. **#139 的重试无法观察。** `app/core/db_retry.py` 重试时不写日志，所以本次只能说明没有死锁影响到用户，而不能
   说明重试是否发生过。重试时写一行警告日志，下一次测试就能回答这个问题。*2026-10-08 更新：已在 PR #202 中加上。*
