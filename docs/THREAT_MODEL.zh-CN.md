## 1. 一段话概述系统

浏览器中的 Vue 单页应用完成全部文件与账户密钥的密码学运算。它用全新的数据加密密钥（DEK）加密
每个文件，把该 DEK 分别包装给所有者的 RSA 公钥和一把离线恢复公钥，然后只上传密文。账户私钥在
浏览器中由加密 passphrase 派生的密钥封装，而该 passphrase 从不离开浏览器。位于 nginx 之后的
FastAPI 后端负责会话认证，把密文存放在本地磁盘、把信封存放在 MySQL 8.4，执行共享与恢复策略，
并把每一项安全敏感变更追加进哈希链审计日志。所有组件运行在同一台 VPS 上。参见
[ARCHITECTURE.zh-CN.md](ARCHITECTURE.zh-CN.md) 与 [SECURITY_FLOWS.zh-CN.md](SECURITY_FLOWS.zh-CN.md)。

## 2. 安全目标

| # | 目标 |
|---|---|
| O1 | 在「客户端代码可信、以 API 为边界」的模型下，后端、数据库与存储从不持有读取文件内容或解开 DEK 所需的明文材料——因此攻破或窃取它们都得不到明文。这一点**不**适用于替换了客户端代码的运维者（N1）。 |
| O2 | 文件内容以及绑定进其 AAD 的元数据，无法在不被察觉的情况下被篡改。 |
| O3 | 只有所有者、当前被授权者以及经批准的恢复流程能取得文件密钥。 |
| O4 | 仅凭一份被盗的服务端会话，既无法读取文件，也无法夺取账户的密钥托管权。 |
| O5 | 安全相关操作被记录在日志中，且对日志的悄然改写是可检测的。 |
| O6 | 遗忘的*登录密码*可以找回；遗忘的*加密 passphrase* 只能由持有该账户私钥文件的人找回。 |

## 3. 明确的非目标

以下内容在设计上即不在范围内。把它们写明本身就是模型的一部分：评审者不应把系统并未声称的
保护归功于它。

| # | 非目标 | 原因 |
|---|---|---|
| N1 | 防御**主动作恶的服务器**，即下发被替换的代码、密钥或密文。 | 浏览器执行的是服务器下发的 JavaScript。愿意下发恶意代码的服务器可以窃取 passphrase。零知识成立于 **API 边界**，而不针对代码提供方。参见 [SECURITY_FLOWS.zh-CN.md 的元数据泄露一节](SECURITY_FLOWS.zh-CN.md)。 |
| N2 | **文件元数据**的机密性：文件名、MIME 类型、大小、时间戳、所有权、共享关系图。 | 以明文列存储，以便服务器列出、搜索并执行策略。文件名、MIME 类型与明文大小被绑定进 AAD-3，篡改会在解密时被发现；时间戳、所有权与共享关系图是由服务器控制的明文，不受任何文件 tag 保护。决定见[第 10.3 节](#103-元数据与流量泄露)。 |
| N3 | 匿名性与抵抗**流量分析**。 | 访问时间、IP 地址与密文大小对服务器和网络可见。 |
| N4 | 保护**已被攻破的终端**：恶意软件、恶意浏览器扩展，或站在已解锁键盘前的人。 | 能读取页面的东西就能读取用户解密出的内容。 |
| N5 | **收回**接收方已经取得的明文或密钥。 | 撤销只阻止今后经服务器的访问，无法抹除已完成的下载或已解开的 DEK。 |
| N6 | **没有**私钥文件时找回遗忘的加密 passphrase。 | 服务器不持有任何能打开 AMK 信封的材料。这是实现 O1 的代价。 |
| N7 | 高可用、异地冗余，以及通过任何标准的认证。 | FYP 范围，单台 VPS。 |

## 4. 资产

| ID | 资产 | 存在位置 | 泄露的影响 | 被篡改或丢失的影响 |
|---|---|---|---|---|
| A1 | 文件明文 | 仅在用户浏览器内存中短暂存在 | 该文件机密性完全丧失 | — |
| A2 | 文件 DEK | 浏览器内存；只以 RSA 包装形式存储（`file_key_wrappings`） | 可打开该文件 | 文件不可恢复 |
| A3 | 加密 passphrase | 用户脑中；解锁期间在浏览器内存中 | 配合数据库可打开账户私钥 | 受 O6 约束 |
| A4 | 账户主密钥（AMK） | 解锁期间在浏览器内存中；只以 KEK 包装后的形式存储 | 可打开私钥包 | 账户被锁在门外 |
| A4a | 密钥加密密钥（KEK） | 每次解锁时由 passphrase 经 Argon2id 派生；只存在于浏览器内存中；**从不持久化** | 可打开已存储的包装 AMK | 无可丢失：可由 passphrase 重新派生 |
| A5 | 账户私钥（RSA-3072） | 注册时导出一次的明文 PEM；数据库中的封装私钥包；解锁期间为不可导出的 `CryptoKey` | 可打开包装给该账户的每个文件 | 仅包装给它的文件丢失 |
| A6 | 恢复私钥 | **设计上：**按 [BACKUP_AND_RECOVERY.zh-CN.md 第 7 节](BACKUP_AND_RECOVERY.zh-CN.md)中*提议*的保管方式离线存放。**预发布环境现状：**以未加密 PEM 形式存放在一名团队成员的工作站上（T-I8） | 可打开**每个**文件的恢复包装 | 包装给它的文件无法恢复 |
| A7 | 登录密码 | 用户脑中；数据库中的 Argon2id 哈希 | 夺取服务端会话 | 可通过邮件重置（O6） |
| A8 | 访问令牌与刷新令牌 | 浏览器 `localStorage`；数据库中的 SHA-256 哈希 | 在过期或被撤销前接管会话 | 重新登录 |
| A9 | 密文对象 | VPS 磁盘上由服务用户拥有、权限 0700 的目录；加密备份 | 没有 A2 则无意义 | 完整性失败；从备份恢复 |
| A10 | 文件元数据与共享关系图 | MySQL 明文列 | 隐私损失（N2） | AAD 绑定字段在解密时可发现；其余字段不可 |
| A11 | 审计日志与链头 | MySQL。带 HMAC 认证的外部检查点每小时从 staging 发布；已在另一台机器上下载并校验过一份（F-10、T-T6） | 暴露活动记录 | 篡改必须可被检测（O5） |
| A12 | 服务器秘密：`SECRET_KEY`、数据库凭据、邮件 API 密钥、审计检查点 HMAC 密钥 | VPS 受保护环境与仅 root 可读的文件 | 伪造验证码、数据库访问、滥发邮件、伪造检查点 | 服务中断 |
| A13 | 备份私钥 | 设计上：与 A6 相同的提议保管方式，离线存放。其当前位置未记录在预发布环境安装记录中 | 可打开每一套备份 | 备份不可读 |
| A14 | 已部署代码 | GitHub `main`，由只读部署密钥拉取到 VPS | 见 N1：控制它的人就控制了 A3 | — |

## 5. 参与者与对手

| ID | 参与者 | 正当能力 | 必须不能做到 |
|---|---|---|---|
| U1 | 匿名互联网用户 | 注册、请求验证码、登录 | 暴力破解登录、接触任何文件、按邮箱枚举账户（T-S2；用户名本来就是公开的；已登录账户为了分享可以查找某个账户，见 T-S2a） |
| U2 | 已认证 USER | 上传、下载、共享与撤销自己的文件；为自己的密钥申请恢复 | 读取他人文件或元数据；提升角色 |
| U3 | 共享接收方 | 在授权有效期间解密共享给自己的文件 | 没有 `can_share` 时再次共享；撤销后继续经服务器访问 |
| U4 | RECOVERY_OFFICER | 批准或拒绝恢复申请；执行离线重包装 | 批准自己的申请；在线取得文件 DEK；读取明文 |
| U5 | ADMIN | 登记恢复密钥、验证审计链、管理角色 | 读取文件内容或用户私钥 |
| X1 | 网络攻击者 | 观察并修改浏览器与 nginx 之间的流量 | 读取或篡改 TLS 保护下的任何内容（HSTS，`includeSubDomains`） |
| X2 | 被盗会话令牌的持有者 | 在被撤销前以该用户身份调用 API | 读取文件（需要 A3 或 A5）；替换密钥信封（需要 A5——见 T-E3） |
| X3 | 数据库或磁盘窃取者（转储、备份泄露、磁盘镜像） | 读取每一行数据与每个对象 | 读取文件（O1）；只剩针对 A3 的离线 passphrase 猜测 |
| X4 | 恶意或已被攻破的服务器运维者 | X3 的全部能力，外加修改存储数据以及**下发给浏览器的代码** | 仅在 N1 范围内受到约束 |
| X5 | 供应链攻击者 | 发布某依赖的恶意版本，或推送到 `main` | 见 T-T5 与 T-E5 |
| X6 | 拥有仓库写权限的团队内部人员 | 合并到 `main`，随即自动部署 | 绕过评审（目前可以——T-E5） |
| X7 | 恶意接收方 | U3 的全部能力 | 超出 N5 的任何事 |
| X8 | **无法控制代码的数据写入者：**被攻破的后端进程、泄露的运行时数据库凭据，或一处注入漏洞 | 读取并**改写任意数据库行**——公钥、恢复密钥、私钥包、授权。它**无法**更改浏览器运行的代码：发布目录归 `mcs21-deploy` 所有、对其他用户只读，由 nginx 提供，而后端以 `fypapp` 身份运行 | 读取文件（O1 依然成立）；改写公钥能让它得到什么，见第 10.2 节 |

## 6. 信任边界

```text
            TB1 (TLS)              TB2 (回环)              TB3 (TLS，强制)
[浏览器] ────────────> [nginx] ──────────────> [FastAPI] ─────────────────> [MySQL 8.4]
   │  TB0：明文、                   │                │ TB4（文件系统，0700）
   │  密钥与 passphrase 留在此处    │                └───────────────> [磁盘上的密文]
   │                                │                │ TB5（HTTPS）
   │                                │                └───────────────> [邮件服务商]
   │                         TB6：GitHub main ── 只读部署密钥 ──> [VPS 发布]
   │                         TB7：备份与审计检查点 ──> [异地存储]
   └── TB8：恢复私钥与备份私钥——设计上离线保管；预发布环境现状见 A6
```

| ID | 边界 | 跨越的内容 | 主要控制 |
|---|---|---|---|
| TB0 | 浏览器内部与其他一切之间 | **留在客户端：**文件明文、加密 passphrase、AMK、KEK、明文私钥与 DEK。**会发送到 API：**密文、包装后的密钥、公钥与签名，以及登录密码、验证码、访问令牌与刷新令牌、用户名与邮箱，还有明文元数据——文件名、MIME 类型、大小 | 所有涉及秘密的*密码学运算*都在客户端；认证秘密确实会在 TLS 保护下跨越边界。[SECURITY_FLOWS.zh-CN.md](SECURITY_FLOWS.zh-CN.md) |
| TB1 | 浏览器 ↔ nginx | API 承载的全部内容 | TLS；一年期 HSTS 且含 `includeSubDomains`；80 端口以 308 跳转 |
| TB2 | nginx ↔ FastAPI | 被代理的请求 | 配置为绑定 `127.0.0.1:8000`，受信代理为 `forwarded-allow-ips=127.0.0.1`；线上绑定情况的核查在 OBSERVABILITY 第 8 节中仍为待定 |
| TB3 | FastAPI ↔ MySQL | 信封、元数据、审计记录 | `require_secure_transport=1`；最小权限运行时账户，无 DDL 权限 |
| TB4 | FastAPI ↔ 对象存储 | 密文 | 服务用户拥有权限 0700 的根目录；上传时记录 SHA-256，下载时校验 |
| TB5 | FastAPI ↔ 邮件服务商 | 发往用户地址的验证码 | HTTPS API；验证码只以 HMAC 摘要存储 |
| TB6 | GitHub ↔ VPS | 发布代码 | 只读部署密钥；带数据库核验与隔离机制的发布门禁 |
| TB7 | VPS ↔ 异地存储 | 加密备份、HMAC 检查点 | 备份主机只持有公钥（已在预发布环境安装并运行）。30 天存储桶锁定属于设计的一部分，但预发布环境安装记录中未核实这一项。HMAC 检查点每小时从预发布环境上传，并已在主机外校验过一份（F-10） |
| TB8 | 联网系统 ↔ 离线保管 | 恢复私钥与备份私钥 | 仅靠流程，且尚未在预发布环境生效（A6）。代码中*确实*强制的是：没有任何端点接受恢复私钥 |

## 7. STRIDE 分析

每条威胁都有稳定的 ID；第 12 节把所有未决、已接受或推迟的威胁集中列入发现登记表。

### 7.1 仿冒（Spoofing）

| ID | 威胁 | 控制 | 状态 |
|---|---|---|---|
| T-S1 | 对登录进行密码猜测 | Argon2id 哈希；`auth_login_throttles` 中按账户和按 IP 的限流（每账户 10 次失败，每地址 500 次）；nginx `secureview_auth` 每 IP 每分钟 60 次凭证校验；fail2ban 在十分钟内 60 次凭证被拒后封禁（第 11.6 节） | 已缓解 |
| T-S2 | 通过注册、发送验证码或重置密码枚举账户 | 发送验证码与重置密码无论账户是否存在都返回相同响应，并同样消耗额度 | 已缓解 2026-10-09：`POST /auth/register` 现在先消耗验证码再查邮箱，已注册的邮箱返回与验证码错误相同的 `422 invalid_verification_code`。只有用户名被占用会被告知（`409`，在验证码之前），而用户名本来就是公开的，分享时按它解析。→ F-08 |
| T-S2a | 已登录账户按邮箱或用户名查找其他账户 | 分享需要找到接收方，所以 `GET /keys/users/by-identifier/{identifier}/active`（以及已弃用的 `by-username` 别名）按完整的用户名或邮箱精确解析：不做前缀或子串搜索，也不能列出用户。它需要已登录的会话；nginx 限制每个地址每秒 30 个 API 请求，突发 60（第 11.6 节）；返回的只有用户 id 和当前公钥（密钥 id、算法、长度、PEM、指纹、创建时间），从不返回邮箱、用户名或账户的其他信息。已停用、已删除或没有有效密钥的账户，与不存在的账户一样返回 `404` | 接受 2026-10-09：这是有意的设计，因为发送方知道同事的邮箱或用户名，而不知道其 id。任何已注册用户仍能一次猜一个，得知某个地址是否有账户。→ F-21 |
| T-S3 | 窃取令牌劫持会话 | 令牌只以 SHA-256 存储；访问令牌 30 分钟、刷新令牌 7 天、绝对时限 7 天；重放刷新令牌会撤销整个会话族（`AUTH_REFRESH_REPLAY_DETECTED`） | 部分——令牌存放位置见 T-I4 |
| T-S4 | 替换**恢复公钥**，使此后每次上传都包装给攻击者 | 浏览器由 PEM 重新计算并显示指纹；从不信任 API 返回的指纹字段 | 在 FYP 范围内接受——[第 10.2 节](#102-公钥身份回滚与信任锚)。三种替换中影响最大的一种，若项目继续开发应最先修复。 |
| T-S5 | 共享时替换**接收方公钥** | 按精确用户名或邮箱解析接收方；浏览器把 DEK 包装给 API 返回的任何 `public_key_pem` | **已针对 X8 缓解**（2026-10-04，PR #160）——[第 10.2 节](#102-公钥身份回滚与信任锚)。共享对话框会从 PEM 重新计算接收方指纹；如果服务器声明的指纹与公钥不符，就拒绝使用；指纹显示给发送方确认，并可与接收方“设置”页里的指纹核对；DEK 只包装给被确认的那把公钥；首次使用时把指纹固定在发送方设备上（首次信任），之后若变化会发出警告。仍未解决：在新设备上第一次分享仍信任第一把公钥；是否核对由发送方决定；针对 X4（N1），浏览器内的任何检查都无效。 |
| T-S6 | 伪造邮件验证码 | 10 分钟有效期、尝试次数上限、以 `SECRET_KEY`、用途与地址为密钥的 HMAC 摘要 | 已缓解 |
| T-S7 | 上传时替换**拥有者公钥**，使拥有者自己的那份包装落入攻击者之手 | 浏览器从 `GET /keys/me` 取得拥有者公钥并把 DEK 包装给它 | 在 FYP 范围内接受——[第 10.2 节](#102-公钥身份回滚与信任锚)。拥有者第一次打不开新文件时才会发现，为时已晚。 |

## 8. 滥用场景

逐个端到端推演，并注明各自串联了哪些威胁。

1. **笔记本上的会话被盗。** X2 用一个有效令牌打开站点。他们能列出文件与元数据（T-I3），但没有
   passphrase 或密钥文件就无法解密，没有密钥文件也无法重置 passphrase（T-E3）。*残余风险：*
   在会话过期或被撤销前，元数据暴露。
2. **数据库转储泄露。** X3 取得全部信封。文件是安全的（T-I1）。攻击者针对每个账户的 Argon2id
   信封进行离线字典攻击（T-I2）。*残余风险：*弱 passphrase 会被攻破，强的不会。第 9 节把两者都量化了：
   泄露密码库中的 passphrase 在一台笔记本上不到两天即可攻破，而 4 个随机单词面对一百万台笔记本也能
   撑约两年。
3. **恢复密钥被调包。** X4 登记了自己的恢复公钥。此后每次上传都会把 DEK 包装给 X4（T-S4）。
   上传页面显示的指纹会变，但只有带外比对的用户才会察觉。*残余风险：*影响大，能否发现取决于用户。
4. **未来功能中的 XSS。** 一次脚本注入绕过了 Vue 的转义。它读取两个令牌（T-I4），如果密钥已解锁，
   就能解密它想要的任何内容。它无法导出私钥。*残余风险：*取决于 CSP 能否守住。
5. **未经评审的推送。** 某协作者的电脑被攻破并推送到 `main`（T-E5）。自动部署把它发布出去；这些代码
   可以截获 passphrase（N1）。*残余风险：*整个模型都建立在 `main` 可信的前提上。
6. **已被撤销的接收方。** X7 在撤销之前下载了文件，他们会一直保有它（T-I9、N5）。撤销按设计生效，
   也只能做到这一步。

## 9. Argon2id 成本与 passphrase 最短长度

对应 Issue #60 验收标准第 2 条。要回答的问题是：当前登记的 KDF 成本加上 10 个字符的 passphrase
最短长度，能否让威胁 T-I2（数据库被盗后的离线猜测）处于可接受水平，以及用户在解锁时要为此付出什么。

### 9.1 方法

- **防御方。** `/benchmark/argon2` 运行生产环境的 `deriveKek`——与解锁对话框使用的同一个函数、同一个
  hash-wasm 4.12.0 构建和同一组参数——先不计时运行一次以预热 WebAssembly，再对每组参数各计时运行
  五次，每次使用新的随机盐。测试在本地生产构建（`vite preview`）上运行，执行的是与预发布环境相同的
  代码包。
- **攻击方。** `backend/scripts/benchmark_argon2_offline.py` 使用原生 C 参考实现 argon2-cffi，以相同
  参数先在单核、再在全部核心上运行。
- **同一个函数。** [`test_vectors.json`](crypto/test_vectors.json) 中的 `argon2id_kek` 向量由
  argon2-cffi 生成，浏览器的 `deriveKek` 逐字节复现了它们，因此攻击方的数据适用于真实信封，而不是某个
  相似物。
- **原始数据**保存在 [`benchmarks/argon2id-2026-09-30.json`](benchmarks/argon2id-2026-09-30.json)。

### 9.2 解锁让用户付出的代价

五次运行的中位数，2026-09-30。

| 成本 | Chrome 153，macOS | Safari 18.6，macOS | iOS 26.6（夸克，WebKit） |
|---|---|---|---|
| **64 MiB，t=3（生产环境）** | **100 ms** | **106 ms** | **151 ms** |
| 64 MiB，t=6 | 195 ms | 205 ms | 269 ms |
| 128 MiB，t=3 | 206 ms | 1 327 ms ⚠ | 268 ms |
| 256 MiB，t=3 | 426 ms | 433 ms | 555 ms |

生产环境成本在每个被测客户端上都是 **0.10–0.15 秒**。每次解密下载和每次分享都解锁一次。打开的密钥只存在于页面
内存中，这一次操作结束就丢掉。当前设置给用户带来的代价可以忽略不计。

关于数据的说明，如实写出而不加修饰：

- **覆盖面很窄。** 只有一台 Apple Silicon Mac 上的两个桌面浏览器引擎，外加一部 iPhone。**没有测量任何
  Android 设备、Firefox，也没有测量低端或较旧的硬件**，而 Argon2id 恰恰在这些设备上最慢。项目从未声明
  支持哪些客户端，因此本文把「支持的客户端」定义为已测集合，并把这一缺口带入发现登记表。
- **Safari 在 128 MiB 时表现异常。** 五次运行都耗时 1.3 秒，比同一浏览器在 256 MiB 时还慢六倍。原因尚
  不清楚。它不影响生产环境成本，但在把参数改为 128 MiB 之前必须先复现它。
- iOS 上的所有浏览器都基于 WebKit，因此夸克的结果可近似代表 iOS Safari。macOS 的 user-agent 字符串显示
  「Intel」是因为浏览器冻结了该字符串；这台机器实际是 Apple Silicon。

### 9.3 参数与公开指南的对照

- **RFC 9106 第 4 节第二推荐选项：** Argon2id，t=3，p=4，m=64 MiB，128 位盐，256 位输出。SecureView 与之
  一致——16 字节盐、32 字节输出——唯一不同是 p=1。hash-wasm 在单线程中依次计算各条通道，因此四条通道
  在相同内存和轮数下耗费的时间与一条相同，对防御方没有任何好处。对这一实现而言，p=1 是如实的设置。
- **OWASP 密码存储速查表的最低要求：** m=19 MiB，t=2，p=1。已超出。
- **服务器的取值范围**（`KeyProtectionProfileIn`）接受 64 MiB–1 GiB 内存、1–10 轮和 1–16 条通道，因此
  提高成本不需要修改后端。

### 9.4 攻击者猜测的代价

一台 10 核 Apple Silicon 笔记本用全部核心每秒可猜 **52.8–58.3 次**，单核每秒 11 次。十个核心只带来 5.3
倍加速，因为每次猜测要占用 64 MiB，瓶颈在内存带宽而非核心数。下表按**每秒 60 次**计算，这是往对攻击者
有利的方向取整。

表中的倍数是假设，不是测量值。本文不对 GPU 或 ASIC 破解 Argon2id 的速度作任何声称；倍数更大时，
每一行都会按比例缩短。

每个账户有自己的盐，因此每个数字都是**针对单个账户**的。

| Passphrase | 1 台笔记本 | 1 000 倍 | 1 000 000 倍 |
|---|---|---|---|
| 位于任何猜测清单的前 10 000 条（`aaaaaaaaaa`、`password12`、`qwertyuiop`） | 2.8 分钟 | 0.2 秒 | 瞬间 |
| 位于一份 1000 万条泄露密码库中的任意位置 | 1.9 天 | 2.8 分钟 | 0.2 秒 |
| 10 个随机小写字母（26¹⁰） | 74 600 年 | 75 年 | 27 天 |
| 4 个随机 Diceware 单词（7776⁴，约 51.7 位） | 190 万年 | 1 930 年 | 1.9 年 |
| 10 个随机可打印 ASCII 字符（94¹⁰） | 2.8 × 10¹⁰ 年 | 2.8 × 10⁷ 年 | 28 400 年 |

表中时间为穷举整个空间所需；成功的期望时间是它的一半。

### 9.5 结论

1. **KDF 成本不是薄弱环节。** 在当前设置下，任何具有约 50 位真实熵的 passphrase——4 个随机单词——都能
   抵御一百万台笔记本数年，而其所有者解锁只需十分之一秒。
2. **10 个字符的最短长度是可用性下限，而不是强度保证。** 检查只看长度，外加「不同于登录密码」。*（2026-10-08 更新：R-1 已在 #205 中实现，上述两个例子现在都会被拒绝，见 F-04。）*
   `aaaaaaaaaa` 和 `password12` 都能通过，却会在一台笔记本上几分钟内被攻破。当密码由人来选时，长度不能
   很好地代表熵。
3. **只有浏览器能做得更好。** 按设计（O1），passphrase 从不到达服务器，因此服务器既无法对照弱口令名单
   检查它，也无法对它施加任何约束。任何强度检查都必须在客户端进行。

由此提出两条建议，在第 12 节中登记为 F-04 与 F-15：

- **R-1（关键的一条）：在浏览器中拒绝已知的弱 passphrase。** 套用登录密码的弱口令名单，拒绝重复与连续
  的模式以及账户自身的标识符，并引导用户使用 4 个或更多随机单词。这对缩小上表第 1–2 行与第 4–5 行之间
  差距的作用，远大于任何成本提升。
- **R-2（可选）：提高登记时的成本。** 实测显示存在余量：256 MiB、t=3 在每个被测客户端上最多 0.56 秒，
  并使攻击者每次猜测的成本变为四倍。成本按保护配置分别存储，因此新登记会采用新值，已有账户会在下次
  修改或重置 passphrase 时升级。**在测量过一台低端 Android 设备、并复现 Safari 128 MiB 异常之前，不要
  修改它。**

## 10. 密钥保管、公钥身份与元数据

对应 Issue #60 验收标准第 3、4、5 条。每一条要求的都是**决定**，而不只是分析。下面的决定都在 FYP
范围内作出：这些事项都没有出现在 `TODO.md` 或任何 Issue 中，项目有意不去实现它们。每项决定都写明它
接受了什么；在要紧之处，也写明若项目继续开发，最省事且有效的控制是什么。

### 10.1 导出的私钥与遗忘 passphrase 的边界

**这个文件是什么。** 注册时，浏览器只展示一次账户私钥，形式是明文 PKCS#8 `.pem`，并提供下载。它不受
任何 passphrase 保护。持有它的人：

- 在拿到密文与包装后的密钥的前提下，可以打开包装给该账户的每一个文件密钥；而要拿到这些，需要一次
  登录会话或一份数据库转储；
- 配合一次登录会话，可以设置新的加密 passphrase（见
  [SECURITY_FLOWS.zh-CN.md](SECURITY_FLOWS.zh-CN.md#使用私钥文件重置-passphrase)）。

因此，它是该账户一切密码学能力的主凭据，比 passphrase 更强——后者只能打开它的一份存储副本。

**丢失各项的后果。**

| 丢失 | 结果 |
|---|---|
| 只丢登录密码 | 通过邮件验证码重置；文件不受影响 |
| 丢了加密 passphrase，但保留密钥文件 | 在 Settings 用密钥文件设置新 passphrase（单密钥账户）；文件不受影响 |
| passphrase 与密钥文件都丢了 | **文件无法恢复。**管理员恢复帮不上忙：它把 DEK 重新包装给用户*已登记*的公钥，而该公钥对应的私钥恰恰就是丢失的那一把；它也无法登记替代密钥 |
| 密钥文件被盗 | 窃贼还需要一次会话或一份转储才能取得密文。重置 passphrase 无济于事——密钥对并未改变——而浏览器中也没有吊销密钥的流程 |

**决定。** 保留明文 `.pem` 导出。它是唯一独立于 passphrase 的恢复因子；若改为加密导出，用户就得再多
保管一个秘密，而这恰恰是人们把两样东西一起弄丢的原因。保管指引留在产品界面中，而不仅仅写在这里。
注册页现在已正确说明这些边界。在本次修改之前，它仍告诉用户 passphrase「无法重置」，而自从密钥文件
重置功能上线，这句话就已不再成立。

*若项目继续开发：*可以提供一份加密的恢复套件——由一个随机恢复码派生出第二个 KEK，用来包装同一个
AMK——让用户打印一份可安全保存的东西。这需要第二个保护配置，属于 Schema 变更。

### 10.2 公钥身份、回滚与信任锚

浏览器执行的每一次包装，用的都是服务器提供的公钥：拥有者自己的公钥来自 `GET /keys/me`，接收方的公钥
来自按标识符查找，恢复公钥来自 `GET /recovery/public-key`。问题在于谁能替换它们。

- **面对恶意的代码提供方（X4），这里的任何措施都无济于事。**能替换密钥的代码，同样能删掉本应发现
  替换的那道检查。这就是 N1，结论不变。
- **面对无法控制代码的数据写入者（X8），浏览器中的检查确实有用**，因为 X8 能改写浏览器读取的数据行，
  却改不了浏览器的代码。发布目录归 `mcs21-deploy` 所有、对其他用户只读，而后端以 `fypapp` 身份运行。
  本节讨论的就是 X8。

X8 替换各把公钥能得到什么：

| 公钥 | X8 的收益 | 会被发现吗？ | 最省事且有效的控制 |
|---|---|---|---|
| 恢复公钥（T-S4） | 此后每次上传的恢复包装——X8 能解密**所有用户的每一个新文件** | 只有有人去比对上传页显示的指纹时才会发现 | 把允许的恢复公钥指纹列表**编译进前端**，不匹配就拒绝上传。轮换恢复密钥就成了一次需要评审的代码变更。 |
| 接收方公钥（T-S5） | 此后共享给该接收方的每一个文件 | 较晚——真正的接收方打不开文件 | 在共享对话框中显示接收方指纹；首次使用时固定在发送方设备上，指纹变化时发出警告 |
| 拥有者公钥（T-S7） | 每次新上传中给拥有者的那份包装 | 较晚——拥有者打不开新文件 | 在注册或首次解锁时把拥有者自己的指纹固定在设备上（注册页本就会显示它），并在每次上传前比对 |

**回滚（T-T4）。** 回滚文件没有实际意义：文件不可变，且 AAD-3 把每份密文绑定到它自己的 `file_id`。
下发更早的保护配置，只对知道旧 passphrase 的人有用，而这个人本就持有那份信封的副本。唯一危险的回滚，
是重新启用一把*已退役的公钥*，例如因怀疑泄露而轮换掉的恢复密钥。这正是上表中的替换情形，控制措施也
相同。

**信任锚。** 浏览器能信任的东西里，只有一样独立于服务器的数据：构建它的代码，它来自经过评审的 Git
历史。任何持久的固定都必须放在那里。设备本地的「首次使用即信任」更弱——换一台新设备、或清空存储之后，
它就什么都约束不了。而构建时的信任锚，其强度又取决于从 Git 到生产环境的这条路径，因此 **T-E5（没有
分支保护、部署不以 CI 为门槛）是前提条件**，而不是另一个独立问题。

**决定。** 在 FYP 范围内接受 T-S4、T-S7 与 T-T4。T-S5 此后已用上表中的接收方控制措施缓解：显示并确认指纹、首次使用时固定、变化时警告（PR #160）。它们都不在 `TODO.md` 或任何 Issue 中，而 X8 是
已经攻破了后端或其数据库的对手。若项目继续开发，应首先固定恢复公钥：它的波及面最大、无声无息，而且
改动最小。

### 10.3 元数据与流量泄露

**决定。** 文件名与 MIME 类型保持明文。服务端的文件名搜索（`File.original_filename LIKE …`）与文件列表
都依赖它们。若把它们移入 Schema 早已预留的 `encrypted_manifest` 列，就必须先解锁才能显示任何文件名，
搜索也要搬到浏览器中进行——这是一项很大的改动，换来的隐私收益却是 N2 已声明不在范围内的东西。无论
哪种方式，它们的*完整性*都受到保护：三者都被绑定进 AAD-3。

*若项目继续开发：*路径是 `envelope_version = 2`，把文件名与 MIME 类型放进加密 manifest，只对外暴露
填充后或粗粒度的值，[FILE_ENVELOPE.zh-CN.md](crypto/FILE_ENVELOPE.zh-CN.md) 已提到这一点。

因此，服务器能观察到的内容如下，明确列出而不是隐含：

| 可观察的内容 | 来源 | 精度 |
|---|---|---|
| 文件名、MIME 类型 | `files` 表的列 | 精确 |
| 文件大小 | `file_size_bytes`；所有支持的算法（AES-GCM、AES-GCM-SIV、(X)ChaCha20-Poly1305）的密文长度都与明文相同 | **精确**——没有填充 |
| 上传、更新与删除时间 | `files` 表的时间戳 | 精确 |
| 谁拥有什么、谁共享给了谁、带什么权限 | `files`、`file_access_grants` | 精确 |
| 每个文件何时被谁请求下载 | `FILE_DOWNLOAD_AUTHORIZED` 审计行 | 精确，逐次请求 |
| 恢复活动 | `recovery_requests`、审计行 | 精确 |
| 每个会话及每次被审计操作的 IP 地址与 user agent | `user_sessions`、`audit_logs` | 精确 |
| 所选的加密算法与 KDF 成本 | `files`、`user_key_protection_profiles` | 精确 |
| 在网络上、对 TLS 之外的观察者而言 | — | 传输大小与时间；下载大小等于文件大小 |

## 11. 供应链、CSP、上传滥用、令牌与恢复操作

对应 Issue #60 验收标准第 6 条。每个小节都写明现有措施、实测结果，以及它在第 12 节中对应的发现。

### 11.1 依赖与供应链

| 方面 | 现有措施 | 缺口 |
|---|---|---|
| 前端 | 有 `package-lock.json`；CI 与部署都用 `npm ci` 安装，每次构建使用完全锁定的依赖树 | `package.json` 使用 `^` 范围，但实际安装的版本由锁文件固定 |
| 后端 | `requirements.txt` 中全部 14 个直接依赖都以 `==` 固定 | 传递依赖未固定，也没有哈希，因此日后重新安装可能解析出不同的间接版本 |
| 密码学库 | 选择 `@noble/ciphers` 是因为它零传递依赖；其余密码学代码只有 `hash-wasm` 与 python-cryptography | — |
| 应用页面上的脚本 | CSP `script-src 'self'`：应用不加载任何第三方脚本 | `/docs` 与 `/redoc` 会加载——见第 11.2 节 |
| 自动化 | CI 在每个 PR 及每次推送到 `main` 时运行 lint、类型检查与测试 | 没有 Dependabot 或 Renovate；CI 中没有 `npm audit` 或 `pip-audit`；GitHub Actions 按大版本标签（`@v4`）而非提交固定 |

**时间点扫描，2026-09-30：**`npm audit`（生产与开发依赖）以及在隔离虚拟环境中运行的
`pip-audit -r backend/requirements.txt`，结果均为**没有已知漏洞**。这只是一次快照，而非一项策略：
没有任何机制会重复运行它。→ F-12。

### 11.2 内容安全策略（CSP）及其例外

应用的 CSP 很严格：`default-src 'self'`、`script-src 'self' 'wasm-unsafe-eval'`、`connect-src 'self'`、
`object-src 'none'`、`frame-ancestors 'none'`。下表列出每一处放宽及其存在的理由。

| 位置 | 放宽 | 原因 | 风险 |
|---|---|---|---|
| 应用 | `'wasm-unsafe-eval'` | hash-wasm 把 Argon2id 编译为 WebAssembly，没有它任何账户都无法解锁。`/benchmark/argon2` 已在预发布环境上确认其可用（第 9 节） | 只允许编译 WebAssembly，不允许 `eval` JavaScript |
| 应用 | `style-src 'unsafe-inline'` | Vue 组件与库使用的内联样式 | 只可能发生 CSS 注入；令牌不在 DOM 中，选择器读不到 |
| 应用 | `img-src data: blob:` | 来自 `data:` 与 `blob:` URL 的图片 | 图片不携带脚本 |
| `/docs`、`/redoc` | `script-src 'unsafe-inline' https://cdn.jsdelivr.net` | FastAPI 的 Swagger UI 与 ReDoc 页面 | **第三方代码在应用同源下运行的唯一位置** → F-03 |

`/docs` 加载 `https://cdn.jsdelivr.net/npm/swagger-ui-dist@5/swagger-ui-bundle.js`。其版本会随今后每一个
5.x 版本浮动，并且**没有子资源完整性（SRI）**属性（已在预发布环境核查：`integrity=` 属性数为零）。它运行在
`https://secureview.tech` 上——正是在这个源的 `localStorage` 中，保存着每个已登录用户的访问令牌与刷新令牌
（T-I4）。一旦这个包的某次发布或该 CDN 被攻破，任何打开 `/docs` 的已登录用户的令牌都可能被读取。它无法解密
文件（仍需要 passphrase 或密钥文件），但能接管会话。因此 T-I6 的严重度高于 v0.1 中记录的「低」。

### 11.3 上传滥用

单次上传在 nginx 与后端均限制为 500 MiB，`/api/` 限流为每 IP 每秒 30 次、突发 60 次。自 2026-10-04 起，后端还会拒绝
以下上传：会让账户存储的密文超过 2 GiB 的（`USER_STORAGE_QUOTA_BYTES`，413 `storage_quota_exceeded`）；会让该账户
24 小时内上传总量超过 5 GiB 的，已删除文件也计入，防止"删了再传"重置额度（`USER_DAILY_UPLOAD_BYTES`，429
`upload_daily_limit`）；以及会让存储所在文件系统的剩余空间低于底线的（`UPLOAD_MIN_FREE_DISK_BYTES`，507
`server_storage_low`；staging 与其他服务共用磁盘，设为 20 GiB）。这些检查使用客户端声明的大小，随后再与实际收到的字节
数核对，并且在写入任何内容之前执行。nginx 限制每个地址同时最多 50 个上传，安全 Agent 的 `UPLOAD_BURST` 规则会报告
单个账户十分钟内 30 次以上的上传。剩下的风险是多个账户一起写满磁盘，这需要同样多个通过验证的邮箱，并且仍会被磁盘
底线和 85% 告警拦住 → F-09。另外，浏览器内
加密的内存峰值约为文件大小的四倍——实测正好是 4.00 倍——对 500 MiB 的文件而言约为 2 GB，手机上很可能失败
→ F-19。

### 11.4 令牌存储

访问令牌（30 分钟）与刷新令牌（7 天）存放在 `localStorage` 中，源上运行的任何脚本都能读取。另一种做法是
`HttpOnly` Cookie，它能让令牌远离脚本，但需要 CSRF 防护，并改动后端签发与读取会话的方式。现有控制是：严格的
应用 CSP、服务端只存令牌哈希，以及刷新令牌轮换与重放时整族吊销。私钥不受影响：它以不可导出的 `CryptoKey`
形式保存，`localStorage` 中从不包含它。**决定：**在 FYP 范围内接受，并去掉 CSP 唯一的那处削弱（F-03）→ F-07。

### 11.5 离线恢复操作

恢复流程的代码强制了「申请人 ≠ 审批人」，执行前会重新检查有效授权，且没有任何端点接受恢复私钥。代码无法强制
的，是围绕它的保管：

- [BACKUP_AND_RECOVERY.zh-CN.md 第 7 节](BACKUP_AND_RECOVERY.zh-CN.md)中的保管流程标注为*提议*。实际上，
  预发布环境的恢复私钥是一名团队成员工作站上的**未加密 PEM**，且该工作站上还保留着一份明文副本 → F-02。
- 同一名 RECOVERY_OFFICER 可以既批准又执行一项申请 → F-13。
- 已经交付的执行包在撤销后无法收回。这一点此前已记录在
  [SECURITY_FLOWS.zh-CN.md](SECURITY_FLOWS.zh-CN.md) 中，予以接受。

### 11.6 共用网络：按地址的限制实际上是按整个房间

所有按客户端地址计数的限制都假设一个地址就是一个人。在校园或会场的 Wi-Fi 上不是这样：整个房间都在同一个 NAT 后面，到服务器这边
只有一个 IP。按原来的数值，一个教室的人同时用网站就会自己把限制触发；更糟的是 fail2ban 匹配 `/api/v1/auth/` 下所有 401，
包括每个打开的标签页在 30 分钟访问令牌过期后发的 `/auth/me`，几个闲置的标签页就能把整个会场封一小时。2026-10-09，
答辩之前，按地址的限制按"约一百人共用一个地址"重新设定，按账户的限制保持不变：

| 层 | 限制 | 原来 | 现在 |
| --- | --- | --- | --- |
| nginx `secureview_api` | 每地址每秒请求数，突发 | 10，20 | 30，60 |
| nginx `secureview_auth` | 每地址每分钟凭证校验次数，突发 | 12，8，作用于整个 `/api/v1/auth/` | 60，30，只作用于登录、注册、重置密码、改密码、删号和发验证码 |
| nginx `secureview_upload_conn` | 每地址同时上传数 | 10 | 50 |
| fail2ban `secureview-auth` | 十分钟内凭证被拒次数，然后封禁 | 20 次封 1 小时，`/api/v1/auth/` 下任何 401 或 429 | 60 次封 15 分钟，只算凭证路由上的 401 |
| 后端 `AUTH_LOGIN_IP_MAX_FAILURES` | 每地址 15 分钟内登录失败次数 | 50 | 500 |
| 后端 `AUTH_REAUTH_IP_MAX_FAILURES` | 每地址密码复核失败次数 | 20 | 200 |
| 后端 `AUTH_REGISTRATION_MAX_ATTEMPTS` | 每地址每小时注册次数 | 10 | 200 |
| 后端 `VERIFICATION_SEND_IP_MAX_PER_WINDOW` | 每地址每小时发码次数 | 20 | 300 |
| 后端 `VERIFICATION_CHECK_IP_MAX_FAILURES` | 每地址每小时验证码错误次数 | 50 | 500 |

保护单个账户的部分没有变：登录失败十次封账户五分钟，密码复核失败五次封改密，验证码错五次作废，每个邮箱每小时最多发五个码。
按地址的限制现在拦的是脚本而不是人群：十分钟内 60 个错密码是每十秒一个，猜密码的工具第一分钟就到了，一屋子人打错密码到不了。
剩下的风险还是 T-D1 记的那条：来自很多地址的洪泛这一层拦不住。

## 12. 发现登记表

对应 Issue #60 验收标准第 7 条。把第 7–11 节中所有未决、已接受或推迟的事项集中在一处。

**严重度**按*本部署中*的影响 × 可能性评定：
- *高*——存在一条可现实地获取大量用户文件明文或密钥的路径，或一条可发布任意代码的路径。
