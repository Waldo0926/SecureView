## 1. 端到端加密：服务器从头到尾碰不到明文

**讲什么：** 文件在用户自己的浏览器里加密，每个文件用一把新生成的随机密钥。这把文件密钥再用 RSA-OAEP 分别包装给
用户自己的公钥和恢复密钥。服务器收到的只有密文、包装过的密钥和元数据，它没有能力解密。

**证据：**
- `docs/ENCRYPTION_EVIDENCE.md`、`docs/crypto/FILE_ENVELOPE.md`（文件格式和测试向量）
- CI 里的 `tamper-drill`：篡改服务器上存储的密文，验证客户端一定能发现
- 现场篡改演示 [TAMPER_DEMO.zh-CN.md](TAMPER_DEMO.zh-CN.md)：当着观众在 staging 上改掉存储文件的一个字节，接收方
  下载被拒绝。连数据库里的摘要一起改也照样被拒，因为上传时的摘要还写进了哈希链审计日志
- My Files 页面的密文预览面板
- 上传页面的加密过程展示（第 2 条）

**评委可能问：** 服务器到底能看到什么？
**答：** 能看到文件名、大小、MIME 类型和时间戳这类元数据，文件列表和分享功能要靠它们工作；看不到文件内容和文件密钥。
如实说出来，比说"服务器什么都看不到"更可信。

## 2. "上传一下子就好了，是不是根本没加密？"——上传时展示加密过程（PR #156）

**背景：** 浏览器里的 AES-GCM 有硬件加速，加密几 MB 的文件只要几十毫秒，所以以前一点按钮就瞬间完成，看起来像没加密。

**做法：** 上传时分步展示真实流程：读取文件 → 用所选算法加密（新密钥、新 nonce，加密后立刻解密一次自检）→ 用 RSA-OAEP
包装文件密钥 → 只上传密文（真实上传进度条）。每一步旁边标出**实测耗时**。最后把原文件的前 16 个字节和加密后的前 16 个
字节**并排显示**：PDF 原文能看到 `%PDF-1.7`，加密后是一串随机字节，也就是服务器收到的内容。本地实测一个 3 MB 文件：
加密加自检 21 ms。

**怎么讲：** "我们没有为了让人相信而故意放慢。每一步的时间都是实测的，加密前后的字节对比就是证据。"每一步最少显示
0.35 秒，只是为了让人看清，显示的耗时不包括这段停留。

**评委可能问：** 动画是做出来的效果吗？
**答：** 显示的字节就是这一次上传真实的明文和密文开头，耗时是代码在每一步前后测出来的。翻牌只是显示方式，最后定格的值是真的。

## 3. 用数据说话的容量测试（#140，PR #155）

**讲什么：** 导师在 2026-10-01 的会上要求"给出数字，而不是说支持很多人"。我们写了一个和浏览器做完全相同加密的压测工具，
2026-10-03 至 04 夜间在 staging 上跑完了完整的测试矩阵。

**修复已在 staging 上验证（2026-10-04 晚）：** 100 个并发用户时，上传从 78% 失败（HTTP 500）变为 **102 次全部成功**，
102 次下载解密完整性失败 0 次（[证据](../performance/pool-fix-2026-10-04/README.zh-CN.md)）。

**所有修复之后重新测量（2026-10-09，版本 `ac5e2b0`）：** 这次走公网地址 `https://secureview.tech`，和真实用户的路径一样
（HTTPS、nginx，限流开着）。共 18,256 次操作；7,444 次下载解密后做了 SHA-256 比对，**完整性失败 0 次，服务器错误 0 次（没有 5xx）**。
50 个用户以内所有请求都成功（上传 p95：1 人 134 ms，50 人 3.3 s）。100 个用户时服务器仍然**没有一个 500**。两次 100 用户步骤里
被拒绝的 644 次上传，都是 nginx"每个地址最多 50 个上传同时进行"返回的 429，因为所有负载都来自同一台笔记本。这是按地址限流在
正常工作，真实用户来自不同地址。36 个文件（六种类型，1 到 500 MiB）全部逐字节一致地往返，包括分享和接收方下载。吞吐稳定在
每个方向约 8 到 9 MiB/s，服务器 CPU 平均 4.5%，API 内存一直是 199 MiB，所以瓶颈是 VPS 的 100 Mbit/s 网口，不是程序
（[报告](../performance/REPORT-2026-10-09.zh-CN.md)）。

**关键数字（修复前的对照，2026-10-03/04）：**
- 共 22,264 次操作；5,094 次下载全部解密，并与原文件做 SHA-256 比对，**完整性失败 0 次**
- pdf/png/jpg/mp4/zip/exe 六种类型，从 1 MB 到 500 MB 全部逐字节一致地往返（144/144）
- 5 个用户的混合负载累计稳定运行 108 分钟（19,372 次操作），服务器端零错误；50 个并发用户以内服务器零错误
- 100 个并发用户时开始出错（65–78% 的上传返回 500）。原因是数据库连接池（15 个连接）耗尽，此时 CPU 平均只有 3%，**瓶颈不在硬件**
- 负载降下来以后，服务自动恢复到零错误，不需要重启
- 同时登录：服务器按设计同一时间只验证 2 个密码（Argon2id 很耗内存），多出来的请求会立刻收到 429、由客户端重试，不会崩溃

**证据：** `docs/performance/REPORT-2026-10-09.md`（修复后）和 `docs/performance/REPORT-2026-10-03.md`（修复前的对照），
都含图表；`docs/PERFORMANCE_TESTING.md` 末尾的结论、
原始数据 `docs/performance/raw/`、服务器资源采样 CSV。

**一定要说明的测试条件：** 2026-10-03/04 那次，压测端家里的线路（上行约 24 Mbit/s、下行约 13 Mbit/s）限制了所有传输速度。
2026-10-09 那次家里网络快得多（speedtest.net 实测下行 821 Mbit/s、上行 493 Mbit/s），所以瓶颈变成了 VPS 自己的 100 Mbit/s 网口
（实测下行 94、上行 97 Mbit/s）：多人时文件数据每个方向约 8 到 9 MiB/s，单个 500 MiB 传输达到 87 到 98 Mbit/s。每份报告的"Test conditions"一节都写明了用的是哪条线路。

**评委可能问：** 500 MB 的文件要多久？
**答：** 2026-10-09 上传约 48 秒、下载约 43 秒，这时服务器 100 Mbit/s 的网口已经跑满，CPU 一直很低。2026-10-03 家里线路慢，同一个文件要好几分钟。想更快，要换的是更大的网口，而不是改代码。

**评委可能问：** 100 个用户就扛不住了？
**答：** 当时是扛不住，后来我们修好了。压测把问题指向了数据库连接池，而不是硬件。我们的第一个推测（文件传输期间占着连接）
**是错的**，并且用测量证明了它是错的：慢速下载期间没有任何未结束的事务。真正的原因是：上传在等待线程池时一直占着连接，
而线程池的线程又全在等连接。修复后（PR #163），用同一个工具、在同一台机器上测 100 个用户：**上传失败率从 80% 降到 0%，
吞吐量从每秒 0.33 次升到 56 次**。把 `docs/performance/pool-fix-2026-10-04/` 里的两张图并排放出来。随后在 staging 上
重跑了同样的 100 用户阶段（2026-10-04 晚）：102 次上传、102 次校验下载全部成功
（[staging 重测](../performance/pool-fix-2026-10-04/staging-rerun/REPORT.md)，#172）。2026-10-09 又经公网地址重跑了
压测矩阵（长时间压测除外）：100 个用户时服务器错误是 0，而修复前是 65% 到 78% 的 HTTP 500（[报告](../performance/REPORT-2026-10-09.zh-CN.md)）。

**怎么讲：** 这是整个项目里最有说服力的工程故事：先测量、找到瓶颈、猜错一次并证明自己错了、修掉真正的原因、再测量一次。

## 4. 测试真的找到了 bug，并且修好了（#139 → PR #154）

**讲什么：** 压测工具在本地预演时就发现了两个只在并发下才出现的 MySQL 死锁：两个新账号同时登录，以及下载和分享同时

**修复：** 按 MySQL 官方的建议，遇到死锁（1213）或锁等待超时（1205）时，回滚并重试整个事务，最多 3 次。

**证据：**

  后端单元测试 718 个，覆盖率 81.84%，另有 977 个前端实时测试和 57 个浏览器测试
- staging 上整晚 28,540 个请求，没有出现一次死锁

**怎么讲：** "我们的测试不是走过场：它在上线前找到了真实的并发 bug，我们修好了，并且用测试证明修好了。"

## 7. 防止恶意大量上传 / 拖垮服务器

**原有防护：**
- 只有通过邮箱验证码注册的账号才能上传；注册和发送验证码都有频率限制
- nginx 按 IP 限速：API 每秒 30 次（突发 60），登录和其他校验密码的接口每分钟 60 次（突发 30）
- 单个文件最大 500 MB；nginx 会先收完整个上传再转给后端，慢速客户端占不住后端
- 磁盘超过 85%、错误突增都会发告警邮件；安全 Agent 能识别猜密码、下载突增、分享突增。它在真实流量上触发过：2026-10-09 压测后的第二天早上，
  它发邮件报了 43 条 High 发现，全部是我们自己的测试账号，靠审计日志几分钟就核实了（User-Agent、地址、时间）

**曾经的缺口：** 威胁模型里有记录（`docs/THREAT_MODEL.md` T-D2 / F-09）：没有单用户存储配额，一个账号理论上就能写满磁盘。

**补上的加固（PR #157，已合并并部署）：**
1. 每个账号最多存 2 GB、24 小时内最多上传 5 GB（删了再传也算在内），超出时给出明确提示；磁盘剩余空间低于底线时，拒绝所有上传
2. nginx 限制每个 IP 同时最多 50 个上传（PR #210 从 10 个调高，因为校园网很多人共用一个出口 IP）
3. 安全 Agent 新增 `UPLOAD_BURST` 规则
4. 下载别人分享的可执行文件或带宏文件（.exe、.bat、.js、.docm 等）之前会弹出警告

**大流量 DDoS 要如实说：** 这类攻击在应用层防不住，100 Mbit/s 的网口很容易被打满。真正上线时应该在前面加 Cloudflare 这类
防护服务。把它写成"超出本项目范围的已知风险"，比假装能防住更专业。

**怎么讲：** "我们先做了威胁建模，知道哪里有缺口，按风险排了优先级，再一项项补上。"

## 8. 为什么不扫描病毒——零知识加密的取舍

**讲什么：** 服务器只拿得到密文，就算装了杀毒软件，扫到的也只是随机字节，所以服务端无法扫毒。这是端到端加密的必然结果，
不是疏漏；其他端到端加密网盘（例如 Proton Drive）同样不能在服务端扫描文件内容。

**我们怎么弥补：**
- 文件只能分享给上传者明确指定的注册用户，没有公开链接，风险相当于"认识的人发来的邮件附件"
- 文件在浏览器解密、保存到电脑后，系统自带的杀毒软件（Windows Defender、macOS XProtect）会照常扫描
- 下载可执行文件或带宏文件之前会弹出警告（PR #157）
- 我们**有意不**把文件哈希发给 VirusTotal 之类的服务，否则会把"谁有哪个文件"泄露给第三方

**怎么讲：** "隐私和服务端扫毒不能兼得。我们选择了隐私，并用分享范围、下载警告和终端杀毒来降低风险。"

## 9. 文件到底分享给了谁：密钥指纹（PR #160）

**讲什么：** 如果服务器能把接收方的公钥偷偷换成自己的，那么分享给这个人的每一个文件都会落到服务器手里。我们的
威胁模型列出了这个风险（T-S5），并推荐了对应的控制措施，我们把它做了出来。分享之前，对话框会写明接收方是谁，并
显示文件将被加密给的那把公钥的指纹。指纹**在浏览器里根据公钥本身计算**，不采用服务器给的值。接收方在自己的
“设置”页能看到同一个指纹，两个人可以互相念一遍核对。浏览器会记住每个接收方的指纹，之后如果变了就发出警告，
思路和 SSH 的 known hosts、Signal 的安全码一样。确认的是哪把公钥，用的就是哪把，中间不会再查第二次。

**怎么演示：** 分享一个文件，指出屏幕上的指纹；再在第二个屏幕上打开接收方的“设置”页，展示两边一致。

**评委可能问：** 这能防住所有攻击吗？
**答：** 不能，我们会主动说明。它能防止服务器端的数据攻击者悄悄改变分享对象。但能控制浏览器所运行代码的人可以把
这个检查删掉（威胁模型 N1）；而且在一台新设备上第一次分享时，仍然信任看到的第一把公钥。是否核对，由用户自己决定。

## 11. 我们用脚本而不是肉眼来检查界面（#183）

**发生了什么：** “Sealed”改版之后，页面单看都不错，放在一起却不对（标题有的左对齐有的居中，宽度各不相同，
帮助页的侧边栏会消失）。我们写了 `frontend/scripts/layout-audit.mjs`：它在五种配置（1440 浅色、1440 深色、
768、390 手机、1440 中文）下打开每个页面，截全页图，并量出被挤成多行的标题、横向溢出、被截断的文字、
过小的点击区域、未翻译的英文以及控制台或 HTTP 错误。

**可以这样说：** “我们不靠肉眼判断界面。一个脚本把大约一百个页面视图量一遍，给出数字；被挤压的标题和溢出
没有清零，这次改动就不算完成。”要同时说清它**做不到**的事：它量的是版式，不判断页面好不好。

**巡检也检查颜色规则：** 绿色只表示“已验证”或“已封存”，红色只表示“被篡改”或“危险”。深色模式下主按钮是近白色，扫描所有页面的全部控件，没有一个是“成功绿”（#184）。
**一个真实的发现：** 巡检的控制台一栏显示，每次打开访问记录都会发出一个用户无权发出的请求（哈希链校验返回 403），每个已删除的文件还会各产生一个失败请求（404）。修复办法是让审计记录直接带上文件名，并且只对管理员运行哈希链校验；同一个脚本现在对全部 100 个页面视图报告零错误（#185）。

**不是什么都能量出来：** 脚本看不出表格的问题列读起来像第三列答案，也看不出页脚中间空了一列；这些是像访客一样看页面时发现、再手工修好的（[PR #194](https://github.com/jsonrar/fyp-secure-file-platform/pull/194)）。两点都要说：版式靠数字，意思靠眼睛。

**后来又把肉眼发现的问题变成了第二个脚本：** 项目负责人第三次指出“这个标题折得很难看”之后，我们写了 `frontend/scripts/text-audit.mjs`，在六种宽度、中英文下量每个标题和短段落：有没有被限宽、有没有句子被从中间折断、有没有两句话的标题、最后一行是不是只剩一两个词。两句话的简介现在只在句号处换行（`SentenceLines` 组件），中文也一样（[PR #195](https://github.com/jsonrar/fyp-secure-file-platform/pull/195)）。被问“怎么保证界面一致”时可以这样答：一条规则、一个落实规则的组件、一个检查规则的脚本。

**不要说：** 它可以代替可用性测试（见第 10 条）。

## 12. 文件详情栏：证据就在列表旁边，点一下就到（[PR #193](https://github.com/jsonrar/fyp-secure-file-platform/pull/193)）

**展示什么：** 在“我的文件”里点任意一行，列表旁边会打开详情栏：算法、原始和存储的精确大小、上传时记录的
密文 SHA-256、谁能打开这个文件（以及恢复密钥也能打开），还有全部操作。点另一行，详情栏就切换过去；页面不会变暗。

**可以这样说：** “列表告诉你文件是 Verified；点一下就能看到依据：每次下载和每晚扫描都拿来比对的指纹，以及到底
谁持有密钥。”演示时，在刚分享出去的文件上打开详情栏，能看到接收方被列为“can open”。

**被问到为什么不用弹框：** 它描述的是某一行，旁边的列表就是上下文，所以放在列表旁边、不做模态；弹框留给需要用户
作答的步骤（解锁、确认分享）。手机上它变成从底部弹出的面板。

**不要说：** 详情栏本身会检查完整性。Verified 徽章反映的是上一次检查的结果；点“Check integrity”才会重新检查。

## 13. 管理员能重置密码，但永远看不到密码（[PR #197](https://github.com/jsonrar/fyp-secure-file-platform/pull/197)）

**展示什么：** 管理员页面 → Users → 详情，可以看到账户的邮箱、状态、登录时间和统计数字。“重置登录密码”会生成一个
只显示一次的随机临时密码，让该账户在所有设备上退出登录，并发邮件通知本人。PR #212 之后，本人下次登录会直接进入设置页，
设置新密码之前不能去其他页面。服务器也会强制执行：在那之前，除了读取账户信息、修改密码和退出登录，它拒绝所有需要登录的请求，
所以换一个 API 客户端也绕不过这一步。

**可以这样说：** “我们的管理员看不到任何密码，因为本来就没有可看的东西。登录密码只存单向哈希，加密口令从来不会到达服务器。
所以管理员能帮人重新登录账户，但进不了他的文件：重置只改登录密码，文件仍然只能用加密口令打开。”

**被问“为什么不直接让管理员看密码”：** 为了能显示而保存密码，数据库一旦泄露所有人的密码都会暴露；一个安全产品这样做，
等于违反了它自己的威胁模型。

**证据：** 每次重置都记为审计事件 `ADMIN_PASSWORD_RESET`，不含密码；测试检查了只存哈希、会话被撤销、管理员不能重置自己或其他管理员。

## 14. 补完威胁模型和提案要求的事项（PR #200–#205，2026-10-08）

**怎么说：** “我们自己的威胁模型指出，像 `password123` 这样的弱口令，即使有 Argon2id 也几分钟就会被猜中。口令从不到达
服务器，所以只能在浏览器里检查：现在会拒绝常见、有规律或由用户名构成的口令，并建议用四个随机单词（F-04，#205）。还记得
口令的用户可以直接在设置页修改，不用翻出私钥文件（#201）。上传后的封存回执现在可以关闭，这是最后一条没满足的验收标准
（AC7，#200）。”

**证据：** THREAT_MODEL 中 F-04 已标为已缓解并附 PR；单元测试列出了被拒绝和被接受的例子；实时口令重设测试会真实修改一个
账户的口令，并仍能解密修改前上传的文件；主流程浏览器测试会关闭回执并在设置页修改口令。PROPOSAL_TRACEABILITY 中所有产品
验收标准和里程碑 M7 现在都是 Done。

**运维方面各说一句即可：** 死锁重试现在会写日志（#202），2026-10-09 的压测就用上了：8 次死锁，每次重试一次就成功，用户没有看到错误；部署脚本不再无限堆积部署前备份
（76 GB），只保留最新 10 份（#204）。

**评委可能问：** 恶意客户端不能跳过口令检查吗？
**答：** 能，我们也这么说。它保护用户不选弱口令，而不是服务器端的防线，因为按设计服务器永远看不到口令。
